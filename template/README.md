# Go Application Development Guide

English | [简体中文](README.zh-CN.md)

This project is generated by go-init. It uses chi, pgx, and godotenv, with a Handler → Service → Repository structure. Database migrations use Goose, and query code is generated by sqlc.

Initialization registers only `/health` and does not include business tables. `internal/template/` provides compilable placeholders for the layered structure. The business development examples below must be added step by step; they are not created automatically during initialization.

## 1. Starting the project

After successful initialization, dependencies, Goose, sqlc, and PostgreSQL are ready. Run the following in the generated project's root directory:

```bash
go run ./cmd
```

Visit <http://localhost:8080/health>; the response is `非常好👍`. The application listens on port 8080 by default, and the database is mapped to local port 5432.

If the database has stopped, restart it with:

```bash
docker compose up -d postgres
```

If dependency downloads did not finish during initialization, run `go mod download` first. Generated files are retained after initialization fails. Follow the error message to complete the remaining steps rather than running go-init again in the same directory.

You can also run the database and API in containers:

```bash
docker compose up -d --build
```

Choose either local or container execution for the API to avoid both using port 8080 at the same time.

## 2. Environment configuration

The generated project contains only `.env`, not `.env.template`. The default configuration is:

```dotenv
DB_DSN="postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable"
DB_DRIVER=postgres
DB_MIGRATION_DIR=./internal/adapters/postgresql/migrations

# Goose
GOOSE_DRIVER=postgres
GOOSE_DBSTRING=postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable
GOOSE_MIGRATION_DIR=./internal/adapters/postgresql/migrations
```

| Setting | Purpose |
|---|---|
| `DB_DSN` | Application database connection string |
| `DB_DRIVER` | Database driver name |
| `DB_MIGRATION_DIR` | Database migration directory |
| `GOOSE_DRIVER` | Database driver used by Goose |
| `GOOSE_DBSTRING` | Database connection string used by Goose |
| `GOOSE_MIGRATION_DIR` | Migration directory used by Goose |

The default database name, username, and password are all `postgres`. The application loads `.env` through godotenv, and the Goose CLI also reads `.env` from its working directory. All commands in this guide are run from the project root.

Goose settings have already been expanded to actual values during initialization. When changing the database connection, update both `DB_DSN` and `GOOSE_DBSTRING`. When changing the driver or migration directory, update the corresponding Goose setting as well.

The local application connects to `localhost:5432`. The API container is configured in `docker-compose.yaml` to connect to `postgres:5432`, where `postgres` is the Compose service name. When changing the container's database settings, update the connection configuration in Compose as well.

| `internal/env/` | Read environment variables |

The existing `repo.Template` is an empty model. `Queries.Template` returns an empty list without executing SQL. The template business methods are not registered as routes; initially, only `/health` is accessible.

## 4. Developing a business API step by step

The following example uses an `examples` table with list and create endpoints to demonstrate the complete workflow. It assumes the project's module is `my-app`. If you specified another module path during initialization, replace `my-app/` in the Go examples with the module path from `go.mod`. You can check it with `go list -m`.

### 4.1 Creating a migration file

```bash
goose -s create create_examples sql
```

`-s` uses sequential numbering, and `create_examples` is the name of this migration. The file is generated in `internal/adapters/postgresql/migrations/`.

Fill in the table creation and rollback sections of the migration file:

```sql
-- +goose Up
CREATE TABLE examples (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL
);

-- +goose Down
DROP TABLE examples;
```

Continue creating new migration files when adding columns, indexes, or other changes. Correct already-applied migrations through new migrations to avoid inconsistencies between existing databases and migration records.

### 4.2 Applying database migrations

```bash
goose up
goose status
```

`goose up` applies pending migrations to the actual database; `goose status` shows migration status. Goose creates its own migration version table to record which migrations have been applied.

To roll back the most recent migration, use `goose down`. Check that file's Down SQL before running it; in this example, rollback deletes the `examples` table and its data.

### 4.3 Writing query SQL

Replace the placeholder comment in `internal/adapters/postgresql/sqlc/queries.sql` with:

```sql
-- name: ListExamples :many
SELECT id, name FROM examples ORDER BY id;

-- name: CreateExample :one
INSERT INTO examples (name)
VALUES ($1)
RETURNING id, name;
```

The names become generated Go method names. `:many` returns multiple records, while `:one` returns one record. Write operations that do not return records usually use `:exec`; use `:execrows` when you need the number of affected rows.

### 4.4 Generating the Repository

```bash
sqlc generate
```

The current `sqlc.yaml` configuration reads:

- Schema: `internal/adapters/postgresql/migrations/`.
- Query SQL: `internal/adapters/postgresql/sqlc/queries.sql`.
- Go output: `internal/adapters/postgresql/sqlc/`, with the package name `repo`.

This example generates `repo.Example`, `ListExamples`, `CreateExample`, and `repo.Querier`, which includes the query methods, among other code.

Goose updates the actual database; sqlc generates Go code from SQL files. With the current configuration, sqlc does not require you to connect to the database and apply migrations first. For everyday development, follow the sequence: apply migrations → write queries → generate code.

Run `sqlc generate` again after changing the schema or query SQL. It is not needed when changing only the Service, Handler, or routes. Do not run generation when the initial project has no business schema or queries.

### 4.5 Replacing placeholder code

When adding real queries for the first time:

1. Remove the handwritten `internal/adapters/postgresql/sqlc/template.go`, which references the original placeholder model.
2. Replace `repo.Template` and `Template()` in the business layer with the actual model and methods. Complete replacement examples are provided below.
3. Keep the generated `db.go`, `models.go`, `querier.go`, and query implementation files. These files are managed by sqlc and should not be edited manually.

`sqlc generate` does not clean up all handwritten placeholder files or preserve the original placeholder interface. Build the complete project after replacing the business layer.

### 4.6 Defining the request type

Replace `internal/template/types.go` with:

```go
package template

type Request struct {
    Name string `json:"name"`
}
```

You can continue using the `template` package, or rename the directory, package, and corresponding imports to match your business domain.

### 4.7 Implementing the Service and transactions

Write business logic in `internal/template/service.go`. Keep the `Service` interface, the `service` implementation, and the `NewService` constructor.

The initial placeholder code uses `repo.Querier` for its `repo` field. The transaction development example below follows the order implementation on the develop branch and changes this field to `*repo.Queries`, which has the `WithTx` method. The `repo.Querier` interface generated by sqlc contains only query methods.

Replace `service.go` with:

```go
package template

import (
    "context"
    "errors"

    repo "my-app/internal/adapters/postgresql/sqlc"
    "github.com/jackc/pgx/v5"
)

type Service interface {
    ListExamples(ctx context.Context) ([]repo.Example, error)
    CreateExample(ctx context.Context, params Request) (repo.Example, error)
}

// Error definitions
var ErrNameRequired = errors.New("name 不能为空")

type service struct {
    repo *repo.Queries
    db   *pgx.Conn
}

func NewService(repo *repo.Queries, db *pgx.Conn) Service {
    return &service{repo: repo, db: db}
}

func (s *service) ListExamples(ctx context.Context) ([]repo.Example, error) {
    return s.repo.ListExamples(ctx)
}

func (s *service) CreateExample(
    ctx context.Context,
    params Request,
) (repo.Example, error) {
    // Validate input
    if params.Name == "" {
        return repo.Example{}, ErrNameRequired
    }

    // Begin the transaction
    tx, err := s.db.Begin(ctx)
    if err != nil {
        return repo.Example{}, err
    }
    defer tx.Rollback(ctx)

    // Create a query object bound to the transaction
    qtx := s.repo.WithTx(tx)

    // Create the record
    result, err := qtx.CreateExample(ctx, params.Name)
    if err != nil {
        return repo.Example{}, err
    }

    // Perform other business operations that must be committed together
    // Use qtx for all database operations within the transaction
    // Return the error immediately if any step fails

    // Commit the transaction
    if err := tx.Commit(ctx); err != nil {
        return repo.Example{}, err
    }

    // Return the result
    return result, nil
}
```

The transaction sequence is: validate input → Begin → defer Rollback → WithTx → business database operations → Commit → return the result.

Use `s.repo` for ordinary queries. Use `qtx` for all queries and writes within the transaction. If an error is returned partway through, the deferred Rollback rolls back the transaction. Running Rollback after a successful commit does not undo the committed result.

A single INSERT usually does not require an explicit transaction; this example demonstrates the development structure. When operations must succeed or fail together, such as creating an order, creating order items, and deducting inventory on the develop branch, put them in the same transaction and check errors at every step. Manage transactions in the Service.

### 4.8 Implementing the Handler

Write HTTP request handling in `internal/template/handlers.go`. Replace the file with:

```go
package template

import (
    "errors"
    "log"
    "net/http"

    "my-app/internal/json"
)

type Handler struct {
    service Service
}

func NewHandler(service Service) *Handler {
    return &Handler{service: service}
}

func (h *Handler) ListExamples(w http.ResponseWriter, r *http.Request) {
    result, err := h.service.ListExamples(r.Context())
    if err != nil {
        log.Println(err)
        http.Error(w, "internal server error", http.StatusInternalServerError)
        return
    }

    json.Write(w, http.StatusOK, result)
}

func (h *Handler) CreateExample(w http.ResponseWriter, r *http.Request) {
    // Parse the request parameters
    var params Request
    if err := json.Read(r, &params); err != nil {
        log.Println(err)
        http.Error(w, "invalid request body", http.StatusBadRequest)
        return
    }

    // Call the business service
    result, err := h.service.CreateExample(r.Context(), params)
    if err != nil {
        if errors.Is(err, ErrNameRequired) {
            http.Error(w, err.Error(), http.StatusBadRequest)
            return
        }

        log.Println(err)
        http.Error(w, "internal server error", http.StatusInternalServerError)
        return
    }

    // Return the successful response
    json.Write(w, http.StatusCreated, result)
}
```

`json.Read` parses the request, `r.Context()` passes context to the Service, and `json.Write` consistently sets the Content-Type for JSON responses. The Handler does not repeat the Content-Type setting for successful responses or manage database transactions.

Use `http.Error` for error responses; it returns a text response. Request format errors and parameter validation errors in this example return 400, while internal errors return 500. Map other business errors to appropriate HTTP status codes according to the API contract.

### 4.9 Injecting dependencies and registering routes

Add the following to the imports in `cmd/api.go`:

```go
repo "my-app/internal/adapters/postgresql/sqlc"
"my-app/internal/template"
```

In `mount()`, add the following after the existing middleware and `/health` route, but before `return r`:

```go
// Create the database query object
queries := repo.New(app.db)

// Initialize the business service and handler
exampleService := template.NewService(queries, app.db)
exampleHandler := template.NewHandler(exampleService)

// Register the business routes
r.Get("/examples", exampleHandler.ListExamples)
r.Post("/examples", exampleHandler.CreateExample)
```

The request flow is: route → Handler → Service → Repository → PostgreSQL. When adding more business modules, define types, a Service, and a Handler in each business directory, then inject dependencies and register routes here.

### 4.10 Formatting, building, and verifying

```bash
go fmt ./...
go vet ./...
go build -o /tmp/my-app ./cmd
go run ./cmd
```

Restart a locally running service to load changes. When using the API container, run `docker compose up -d --build api` to rebuild and start it.

Check the endpoints in another terminal:

```bash
# Health check
curl -i http://localhost:8080/health

# Create a record; expect 201
curl -i -X POST http://localhost:8080/examples \
  -H 'Content-Type: application/json' \
  -d '{"name":"示例"}'

# List records; expect 200
curl -i http://localhost:8080/examples

# Validate parameters; expect 400
curl -i -X POST http://localhost:8080/examples \
  -H 'Content-Type: application/json' \
  -d '{"name":""}'
```

For transactions involving multiple database operations, also verify in the development environment that earlier writes are rolled back when an intermediate step fails. When all operations succeed, check that all results are committed.

## 5. Everyday changes and commands

| Change | Next steps |
|---|---|
| Add tables, columns, or indexes | Create a migration → `goose up` → update queries as needed → `sqlc generate` → adjust Go code |
| Add or change query SQL | `sqlc generate` → adjust Service calls |
| Change the Service, Handler, or routes | Format → build → restart and verify the API |
| Add real queries for the first time | Remove handwritten placeholder files and replace references to placeholder models and methods |
| Change the database connection | Update the corresponding application and Goose settings in `.env`, update Compose settings as needed → restart the application |

Database data is stored in a Compose volume. Deleting migration files does not clear an existing database. New projects use their own Compose volumes by default; if you reuse an old volume or connect to an existing database, its tables and data remain.
