# 脚手架工具修改方案

## 一、目标与边界

将当前 `e-com` 项目直接改为可发布的 Go CLI `go-init`，不用另外维护一个业务模板仓库。

当前仓库根模块只提供 CLI，不再直接作为应用服务。应用源码和配置统一存放在 `template/` 中，作为独立模块维护；根目录的 `main.go` 是唯一的 CLI 入口。

在空目录执行 `go-init` 后，生成项目的源码、目录、依赖和环境配置，准备 Goose、sqlc，启动 PostgreSQL 并等待就绪。随后执行 `go run ./cmd` 即可启动应用并访问 `/health`。

生成项目保留：

- PostgreSQL 配置、连接初始化和关闭逻辑。
- chi 路由、中间件、日志和 HTTP 服务配置。
- Handler → Service → Repository 的分层结构、接口、构造函数和依赖注入。
- 项目现有 `internal/json` 和 `internal/env` 工具。
- 第三方依赖及固定版本。
- Docker、Compose、Goose 和 sqlc 的使用入口。

移除商品、订单等具体业务；默认只注册 `/health`，数据库没有业务表。模板模块的占位方法不查询数据库、不执行事务，也不注册到 HTTP 路由。

本机需要满足：Go 工具链可用、Docker 与 Compose 可用、Docker 已启动、所需端口可用，以及首次下载依赖和镜像时网络可用。当前项目声明的 Go 版本为 `1.27.1`，此次方案不另行升级或降级。

## 二、项目名称与入口

### 2.1 仓库与模块

- GitHub 仓库从 `e-com` 改名为 `go-init`，同步更新本地 Git remote。
- 本地目录是否改名不影响编译，可在实际实施时一并调整。
- 根目录 `go.mod` 管理 CLI，module 为 `github.com/Violetory/go-init`，依赖按 CLI 的实际需要声明。
- 当前应用的 `go.mod` 和 `go.sum` 移至 `template/`，保留应用依赖和版本，不使用 `go get -u` 更新依赖。
- `template/go.mod` 的 module 使用 `example.com/go-init-template` 作为明确的模板占位路径，模板内部 import 同步使用此前缀。
- 初始化时将模板占位 module 和内部 import 替换为目标项目 module；模板源码不直接引用 CLI 根模块。
- 根目录 `go.sum` 只记录 CLI 实际依赖；如果 CLI 仅使用标准库，可以没有该文件，不能用应用的 `go.sum` 填充。

### 2.2 CLI 单入口与独立模板模块

| 位置 | 职责 | 构建或安装方式 |
| --- | --- | --- |
| 根目录 `main.go` | 唯一 CLI 入口 | 仓库根目录执行 `go build .`、`go install .` |
| `template/cmd/` | 待复制的应用入口 | 在模板模块或生成项目内执行 `go build ./cmd` |

应用模板仍需要入口，供新项目生成后运行；它属于 `template/go.mod` 管理的独立模块，不参与根模块的常规编译。CLI 不直接导入模板应用代码，不启动自身的 HTTP 服务，也不要求为了安装 CLI 而连接数据库。执行 init 时仍按约定准备目标项目的数据库。

### 2.3 路径与配置范围

- 当前 `cmd/`、`internal/`、应用 Docker 和 sqlc 配置等移入 `template/`，根目录不保留应用源码副本。
- 第三至八节及第十二节中的应用相对路径，以应用模板根目录 `template/` 为基准；生成项目中这些路径直接位于项目根目录，不包含外层 `template/`。
- 例如下文 `cmd/main.go` 在脚手架仓库对应 `template/cmd/main.go`，`internal/template/` 对应 `template/internal/template/`。
- 外层 `template/` 是应用资源目录，内层 `internal/template/` 是示例业务模块，两者用途不同。
- 根 `README.md` 说明 CLI 安装、使用和维护；`template/README.md` 只说明生成应用的启动、配置和 SQL 开发。

## 三、应用入口与路由修改

### 3.1 `cmd/main.go`

保留现有的：

- `slog` 初始化。
- `godotenv.Overload(".env")` 加载方式及缺失文件的处理。
- `DB_DSN` 检查。
- `pgx.Connect` 和连接关闭。
- `application` 初始化及 HTTP 服务启动。

只更新需要变化的内部 import。数据库连接失败仍按现有逻辑退出；数据库没有业务表不影响连接。

### 3.2 `cmd/api.go`

保留：

- `application` 中的数据库连接字段。
- `config`、`dbConfig`。
- chi 路由。
- `RequestID`、`ClientIPFromRemoteAddr`、`Logger`、`Recoverer`、`Timeout` 中间件。
- `/health` 及当前响应内容 `非常好👍`。
- HTTP 服务的监听地址及读写超时。

删除：

- `products`、`orders` 的 import。
- 商品和订单的 Service、Handler 初始化。
- `/product/list`、`/product/get`、`/orders/create` 路由。
- 当前不再使用的 `queries := repo.New(app.db)` 及对应 repo import。

默认不新增 `/template` 路由。模板的构造函数保留在模块中，但不在 `mount()` 中创建未使用的对象，也不使用 `_ = handler` 等方式消除未使用变量。

## 四、业务目录与分层结构

### 4.1 目录处理

删除 `internal/products/`，将 `internal/orders/` 改为 `internal/template/`。

保留：

```text
internal/template/
├── handlers.go
├── service.go
└── types.go
```

三个文件统一使用 `package template`。对象名称使用 `Handler`、`Service`、私有实现 `service`；不使用 `TemplateHandler` 或 `TemplateService`。

方法名称使用导出的 `Template`，以便后续路由和跨包调用。删除原来的 `PlaceOrder` 等业务方法。

### 4.2 `service.go`

保留接口、数据库依赖和原有构造函数形态；结构体中的 repo 使用 `repo.Querier`。

```go
package template

import (
    "context"

    repo "example.com/go-init-template/internal/adapters/postgresql/sqlc"
    "github.com/jackc/pgx/v5"
)

type Service interface {
    Template(ctx context.Context) ([]repo.Template, error)
}

type service struct {
    repo repo.Querier
    db   *pgx.Conn
}

func NewService(queries *repo.Queries, db *pgx.Conn) Service {
    return &service{repo: queries, db: db}
}

func (s *service) Template(ctx context.Context) ([]repo.Template, error) {
    return s.repo.Template(ctx)
}
```

删除客户、商品、数量、库存、金额等业务校验，删除订单错误定义和下单事务流程。

`db *pgx.Conn` 仍保留，供后续业务使用事务；通用 `Queries.WithTx` 同样保留。初始占位方法不执行事务。

### 4.3 `handlers.go`

沿用当前项目的响应工具和错误处理方式，不自行设置 `Content-Type`，不在 Handler 中直接编码 JSON，不增加 `json.Error`。

```go
package template

import (
    "log"
    "net/http"

    "example.com/go-init-template/internal/json"
)

type Handler struct {
    service Service
}

func NewHandler(service Service) *Handler {
    return &Handler{service: service}
}

func (h *Handler) Template(w http.ResponseWriter, r *http.Request) {
    result, err := h.service.Template(r.Context())
    if err != nil {
        log.Println(err)
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }

    json.Write(w, http.StatusOK, result)
}
```

这个占位方法展示列表返回和错误传递，因此使用 `StatusOK`，不保留订单创建专用的 `StatusCreated`。

`json.Read` 工具继续保留。当前 `Template(ctx)` 方法没有请求参数，不强制解码空请求体；以后新增带请求体的接口时，沿用现有 `json.Read`、`log.Println`、`http.Error(..., StatusBadRequest)` 流程。

### 4.4 `types.go`

删除 `orderItem`、`createOrderParams` 等业务类型，保留空的请求结构作为扩展位置：

```go
package template

type Request struct{}
```

它不包含业务字段，也不要求当前 Handler 使用。

## 五、migrations 与 Repository

### 5.1 migrations 清空业务内容

删除：

```text
internal/adapters/postgresql/migrations/00001_create_products.sql
internal/adapters/postgresql/migrations/00002_create_orders.sql
```

只保留 `migrations/.gitkeep`，初始模板不包含建表、种子数据或空迁移文件。

删除文件不会删除现有数据库中的表。初始无业务表状态应通过新数据库或新 Docker 数据卷验证，不自动清理已有数据库。

### 5.2 sqlc 清除业务，保留基础类型

此前“sqlc 下只留 queries.sql”的提议，以本节为准调整：保留 `repo.Queries`、`repo.Querier` 和分层调用链，就必须保留它们所依赖的 Go 定义。清空的是业务 SQL 和业务模型，不是全部数据库基础设施。

目标目录：

```text
internal/adapters/postgresql/sqlc/
├── db.go
├── querier.go
├── models.go
├── template.go
└── queries.sql
```

| 文件 | 修改 |
| --- | --- |
| `db.go` | 保留原有通用代码：`DBTX`、`Queries`、`New`、`WithTx` |
| `querier.go` | 移除商品、订单方法，保留模板版 `Querier` 接口和实现检查 |
| `models.go` | 移除商品、订单模型，保留空 `Template` 类型 |
| `template.go` | 新增手写占位查询方法，不执行 SQL |
| `queries.sql` | 保留文件，删除全部业务查询，仅留说明注释 |
| `queries.sql.go` | 删除原有业务查询生成代码 |

`querier.go`：

```go
package repo

import "context"

type Querier interface {
    Template(ctx context.Context) ([]Template, error)
}

var _ Querier = (*Queries)(nil)
```

`models.go`：

```go
package repo

type Template struct{}
```

`template.go`：

```go
package repo

import "context"

func (q *Queries) Template(ctx context.Context) ([]Template, error) {
    return []Template{}, nil
}
```

`queries.sql`：

```sql
-- 在这里添加 SQL 查询，随后执行 sqlc generate。
```

手工改写后的 `querier.go`、`models.go` 和新增 `template.go` 明确标注为模板占位代码，不使用“Code generated by sqlc. DO NOT EDIT.”标记。原有通用 `db.go` 可以保留其生成来源标记。

### 5.3 真实 SQL 接入时的替换规则

初始模板不运行 `sqlc generate`。它没有业务 schema 和查询，但依靠上述占位定义可以编译。

后续接入真实业务时：

1. 创建并填写迁移，添加 `queries.sql` 中的真实查询。
2. 执行迁移和 `sqlc generate`。
3. `db.go`、`querier.go`、`models.go` 等由实际生成结果接管。
4. 删除或调整手写 `template.go`，避免与生成的 `Template` 类型或 `Queries.Template` 方法重名。
5. 同时调整模板模块的返回类型及 Repository 调用，使其匹配新生成的接口；如果已新增自己的业务模块，可以删除原模板模块。
6. 编译验证，不能假设 sqlc 会自动保留手写占位方法或始终生成名为 `Template` 的模型。

占位层的目的仅是保留可编译的架构示例，不声称它由空 SQL 自动生成。

## 六、通用工具和第三方库

### 6.1 `internal/json/json.go`

保留当前两个函数和调用方式：

- `Write`：统一设置 JSON 响应头、状态码并编码响应。
- `Read`：解码请求体，保留 `DisallowUnknownFields`。

Handler 成功响应使用 `json.Write`，错误响应继续使用 `http.Error`。不新增 `Error`、`Success`、`Created` 等额外封装。

当前 `Write` 忽略编码错误的问题可作为后续独立改进。本次不改其签名、不扩大 JSON 工具的改造范围。

### 6.2 `internal/env/env.go`

保留 `GetString` 和当前环境变量读取方式，不加入具体业务配置。

### 6.3 依赖

保留当前直接依赖：

| 依赖 | 当前版本 | 用途 |
| --- | --- | --- |
| `github.com/go-chi/chi/v5` | `v5.3.2` | 路由和中间件 |
| `github.com/jackc/pgx/v5` | `v5.11.0` | PostgreSQL 连接与查询接口 |
| `github.com/joho/godotenv` | `v1.5.1` | 环境文件加载 |

这些依赖位于 `template/go.mod`。间接依赖由 Go 模块管理；在 `template/` 中执行 `go mod tidy`，保留模板校验文件。这些直接依赖仍有实际源码引用，不要求根 CLI 模块也引入 chi 或 pgx。

生成项目复制 `go.mod`、`go.sum` 并执行 `go mod download`，不是把本机模块缓存复制过去。

## 七、环境配置

### 7.1 新增 `.env.template`

默认数据库名统一使用 `postgres`，环境模板、生成的 `.env` 和 Compose 配置保持一致：

```dotenv
DB_DSN="postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable"
DB_DRIVER=postgres
DB_MIGRATION_DIR=./internal/adapters/postgresql/migrations

# Goose
GOOSE_DRIVER=${DB_DRIVER}
GOOSE_DBSTRING=${DB_DSN}
GOOSE_MIGRATION_DIR=${DB_MIGRATION_DIR}
```

不再另外添加 `.env.example`。

### 7.2 init 后只生成 `.env`

`.env.template` 仅保留在脚手架源码的 `template/` 目录和内置模板包中，作为配置生成来源，不复制到新项目。初始化器在内存中读取并解析该文件，只写出应用实际读取的 `.env`，将变量引用展开为：

```dotenv
DB_DSN="postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable"
DB_DRIVER=postgres
DB_MIGRATION_DIR=./internal/adapters/postgresql/migrations

# Goose
GOOSE_DRIVER=postgres
GOOSE_DBSTRING="postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable"
GOOSE_MIGRATION_DIR=./internal/adapters/postgresql/migrations
```

解析、展开由初始化器处理，不通过 shell `source` 执行环境模板。当前应用的 `godotenv.Overload` 加载语义继续保留。

### 7.3 忽略规则

- 脚手架源码中 Git 跟踪 `template/.env.template`，忽略 `.env` 和本机私有环境配置；生成项目中只存在被忽略的 `.env`。
- 当前应用 `.gitignore` 移到 `template/.gitignore`，保留已有的 `!.env.template` 例外规则。
- 根目录另行维护 CLI 的 `.gitignore`，排除本机环境文件、IDE 和构建产物；源码模板及根目录 `template.zip` 必须可以提交。
- 模板打包脚本在排除 `.env.*` 时必须明确保留 `.env.template`。
- 本机实际 `.env` 永远不打入 `template.zip`。
- Docker 镜像无需复制 `.env.template`，容器运行时通过 Compose 注入环境变量。

## 八、Docker 与数据库开箱即用

### 8.1 `docker-compose.yaml`

保留当前 API、PostgreSQL 服务及数据库健康检查。

- `POSTGRES_USER=postgres`。
- `POSTGRES_PASSWORD=postgres`。
- `POSTGRES_DB=postgres`。
- PostgreSQL 映射本机 `5432`。
- 保留命名数据卷和当前持久化路径。
- 保留 API 依赖 PostgreSQL 健康的 `depends_on`。
- API 容器的 `DB_DSN` 使用 `postgres://postgres:postgres@postgres:5432/postgres?sslmode=disable`；本机 `.env` 使用 `localhost`。
- 删除固定的 `container_name: e-com`，由 Compose 自动命名。
- 保留 API 的默认 `8080` 端口配置，不要求给指定环境模板额外增加 `API_PORT`。
- 不添加自动建表或自动执行迁移的启动脚本。

### 8.2 `Dockerfile` 与 `.dockerignore`

- 保留当前多阶段构建及 Go 镜像版本。
- 保留 `go mod download`、CA 证书复制和非 root 运行方式。
- 继续构建应用入口 `./cmd`。
- `/out/ecom`、`/app/ecom` 和 `ENTRYPOINT` 统一改为通用名称 `app`。
- Dockerfile 和 `.dockerignore` 位于 `template/`；模板验证的构建上下文为 `template/`，生成项目的构建上下文为其根目录。
- 模板 `.dockerignore` 排除本机环境文件、Git、IDE、构建产物。CLI 和维护文件位于模板目录之外，本身不会进入应用构建上下文。

## 九、脚手架实现与模板打包

### 9.1 新增文件

```text
main.go
go.mod                         # CLI 模块
go.sum                         # CLI 有外部依赖时生成
template.zip
scripts/update-template.sh
tool-versions.json
```

根目录 `main.go` 使用标准库的参数解析、ZIP 解压和子进程执行能力；不因脚手架功能引入非必需的第三方 CLI 框架。若 CLI 自身需要环境解析等依赖，声明在根 `go.mod` 中，不借用模板模块依赖。

`tool-versions.json` 记录经过验证的 Goose、sqlc 固定版本，由模板打包过程内置到 CLI；它是脚手架维护配置，不复制到生成项目。已固定并验证 Goose `v3.28.0`、sqlc `v1.31.1`。

### 9.2 内置模板

根目录 `main.go` 嵌入同目录下的 `template.zip`：

```go
import _ "embed"

//go:embed template.zip
var templateZip []byte
```

使用 ZIP 避免直接嵌入包含独立 `go.mod` 的模板目录时遇到模块边界，也能完整保存 `.gitignore`、`.env.template`、`.gitkeep` 等隐藏文件。

压缩包根目录直接包含 `template/` 内的 `cmd/`、`internal/` 等内容，不包含外层 `template/`、`e-com/` 或 `go-init/`。

### 9.3 打包内容

唯一打包来源为仓库的 `template/` 目录。包含：应用源码、基础 Repository、`internal/template`、SQL 入口、`.gitkeep`、应用依赖文件、环境模板、Docker 配置、sqlc 配置、忽略规则和 `template/README.md`。

包中的 `.env.template` 是 CLI 的配置输入资源，解压到目标项目时跳过该文件。由 CLI 读取其内容并生成 `.env`，不先把 `.env.template` 落盘到新项目后再删除。

模板目录内排除：

```text
.git/
.idea/
.env
本机私有环境文件
构建产物、缓存和系统元数据
```

根 CLI 源码、根 `go.mod`/`go.sum`、根 README、维护脚本、工具版本配置和方案文档不属于打包来源，无需先复制再排除。

脚本复制当前工作区 `template/` 中的实际文件，包含尚未提交的新模板文件，不使用只反映上次提交状态的打包方式。输出写到根目录 `template.zip`，不写回 `template/`。打包完成后检查必需文件、隐藏文件及禁止内容，并确保不会递归包含旧 ZIP。

### 9.4 更新流程

修改 `template/` 中的源码或配置 → 更新根目录模板包 → 验证解压后的项目 → 提交 CLI 源码、模板源码和模板包 → 发布新版本。

如果只修改源码而不更新 ZIP，已编译 CLI 中的模板不会变化，发布前必须检查二者同步。

## 十、go-init 的运行行为

### 10.1 命令形式

```bash
go-init
go-init --module github.com/yourname/my-app
```

无参数时使用当前目录名称作为本地 module，需验证它符合 module 路径规则；名称无效时提示使用 `--module`。需要仓库路径时使用显式 module 参数。

### 10.2 初始化顺序

1. 检查 Go、Docker、Compose、Docker 服务和必要安装条件。
2. 检查目录；允许已有 `.git/`，拒绝覆盖其他已有文件，不提供默认强制覆盖。
3. 验证模板包结构，拒绝绝对路径、目录穿越和不支持的文件类型。
4. 解压源码、配置及目录占位文件，保留所需文件权限；跳过作为配置输入资源的 `.env.template`。
5. 将模板 module 改为目标 module，只修改 Go 内部 import 和明确的模块引用，不盲目替换第三方路径或任意字符串。
6. 从内置 `.env.template` 读取并展开配置，只生成 `.env`，不在目标目录生成 `.env.template`。
7. 执行 `go mod download`，安装模板指定版本的项目依赖。
8. 安装或确认固定版本的 Goose、sqlc；安装路径优先采用 `GOBIN`，未设置时按 Go 默认安装目录处理。
9. 检查工具是否可被后续终端命令发现，缺失 PATH 配置时给出准确设置方式，不修改用户 shell 配置。
10. 执行 `docker compose up -d postgres`，只启动数据库。
11. 有超时地等待数据库健康并确认生成的 `DB_DSN` 可连接，避免无限等待。
12. 输出生成目录、module、工具版本、数据库状态和应用启动命令。

初始不运行 Goose 迁移、不运行 sqlc 生成、不后台启动 API。

任何步骤失败都返回非零退出码，说明失败阶段和可重试命令。已生成文件保留供检查，不通过清空目录或删除数据库卷掩盖失败。

初始化完成后的应用启动方式：

```bash
go run ./cmd
```

## 十二、后续迁移与查询开发

所有命令在生成项目根目录执行。Goose 从 `.env` 读取 `GOOSE_DRIVER`、`GOOSE_DBSTRING` 和 `GOOSE_MIGRATION_DIR`。

创建顺序编号迁移：

```bash
goose -s create create_example sql
```

空迁移目录下生成 `00001_create_example.sql`。名称是具体迁移名称，不能直接输入 shell 通配符 `*`。

在文件中写入真实业务的 `-- +goose Up` 和 `-- +goose Down` SQL 后，执行：

```bash
goose up
goose status
```

在 `queries.sql` 添加真实查询后，执行：

```bash
sqlc generate
```

Goose 修改实际数据库；sqlc 读取迁移和查询生成 Go 代码，不替代数据库迁移。真实生成后的占位替换按第五节处理。

不将演示建表文件预置到空模板。执行 Goose 迁移后可能出现其版本记录表，这不属于商品或订单业务表。
